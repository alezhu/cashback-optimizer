# Правила оформления коммитов (Commit Guidelines)

Настоящий документ определяет стандарты именования коммитов, правила группировки изменений и регламент выпуска релизов в проекте **Cashback Optimizer**.

---

## 1. Спецификация Conventional Commits

Все сообщения коммитов должны строго следовать спецификации [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/).

### 1.1. Базовый формат

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

* `<type>` — обязательный тип изменения (в нижнем регистре).
* `(<scope>)` — опциональная область/модуль, к которому относится изменение.
* `<description>` — краткое описание изменений (в повелительном наклонении, с маленькой буквы, без точки на конце).

### 1.2. Допустимые типы коммитов (`<type>`)

| Тип | Описание | Пример |
| :--- | :--- | :--- |
| **`feat`** | Новая функциональность | `feat(calc): add roundTo cashback step support` |
| **`fix`** | Исправление ошибки/бага | `fix(exact): correct zero limit handling in branch and bound` |
| **`perf`** | Оптимизация производительности | `perf(exact): add first empty bin symmetry breaking` |
| **`refactor`**| Изменение кода без изменения логики/исправления ошибок | `refactor(services): extract card tier grouping logic` |
| **`test`** | Добавление или обновление тестов | `test(allocation): add tests for single card bin packing` |
| **`docs`** | Изменения в документации | `docs: update agents.md with optimization specifics` |
| **`style`** | Правки стилей, отступов, форматирования (CSS / разметка) | `style(cards): adjust card row input spacing` |
| **`chore`** | Обслуживание, зависимости, сборка, конфиги | `chore(deps): update vitest to v4.1.11` |
| **`ci`** | Настройка CI/CD пайплайнов и GitHub Actions | `ci: fix starting deploy on set version tag` |

### 1.3. Рекомендуемые области (`<scope>`)

* `calc` — базовые расчеты, комиссии, наценки (`calcService.ts`).
* `heuristic` — эвристический алгоритм распределения (`allocationService.ts`).
* `exact` — точный решатель Branch & Bound (`exactAllocationService.ts`).
* `cards` — управление картами и параметры карт (вкладка «Карты»).
* `groups` — группы платежей и комиссии (вкладка «Группы»).
* `ui` / `calc-tab` — компоненты отображения результатов расчетов.
* `db` / `export` — IndexedDB, экспорт и импорт JSON.
* `release` — релизный коммит обновления версии.

## 2. Группировка изменений и атомарность

1. **Один коммит — одна логическая задача**:
   * Изменения не должны сваливаться в один гигантский коммит.
   * Правки алгоритмов, стилизация UI, добавление тестов и обновление конфигов сборщика должны разделяться на отдельные коммиты.
2. **Работоспособность каждого коммита**:
   * Каждый коммит в истории должен быть валидным (код должен компилироваться и проходить тесты).
   * Перед коммитом обязательны проверки:
     ```bash
     pnpm run typecheck
     pnpm test
     ```
3. **Чистота рабочей директории**:
   * В коммит не должны попадать временные файлы, логи отладки или случайно изменённые файлы.

## 3. Процесс выпуска нового релиза

Выпуск новой версии проекта оформляется **строго отдельным коммитом** (standalone release commit).

### 3.1. Алгоритм создания релиза:

1. **Обновить версию** в `package.json` в соответствии с [SemVer](https://semver.org/lang/ru/):
   * `patch` (1.1.0 $\to$ 1.1.1) — исправления багов.
   * `minor` (1.1.0 $\to$ 1.2.0) — новая обратимо совместимая функциональность.
   * `major` (1.1.0 $\to$ 2.0.0) — крупные ломающие изменения архитектуры.
2. **Зафиксировать изменения в `CHANGELOG.md`**:
   * Указать номер версии, дату релиза и списки изменений по категориям (Features, Fixes, Performance).
3. **Сформировать релизный коммит**:
   ```bash
   git add package.json CHANGELOG.md
   git commit -m "chore(release): v1.2.0"
   ```
4. **Установить Git-тег**:
   ```bash
   git tag v1.2.0
   ```
5. **Отправить изменения в удалённый репозиторий**:
   ```bash
   git push origin main --tags
   ```

> **Примечание по CI/CD**: При отправке тега `v*.*.*` в ветку `main` GitHub Action (`.github/workflows/auto-merge-release.yml`) автоматически выполняет слияние в ветку `release`, создает GitHub Release с генерацией заметок и запускает развертывание (`deploy.yml`) на Cloud.ru S3.
